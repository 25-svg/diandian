# 整场母稿基准与候选辅稿设计

## 1. 目标

将一场经过公司确认的多商品整场直播作为企业母稿来源。系统先生成可追溯的审核逐字稿，再按整场流程和商品模块整理为母稿 V1.0。后续录播的成交片段必须与母稿对应章节比较、评分；总分高于 85 分且通过硬性准入检查的片段进入候选辅稿，人工确认后才能形成新的母稿版本。

本设计服务于直播负责人和缺少专业运营经验的工作人员。界面必须用直接、可执行的中文解释结果，不要求用户理解提示词、JSON 或知识库内部字段。

## 2. 核心原则

1. 母稿是整场直播，不是若干互不相关的商品文稿。
2. 整场母稿内部按开场、商品、转品和收尾拆成可维护模块，但仍属于同一个母稿版本。
3. 大模型可以纠错、断句、分类和结构化整理，不得把改写内容标成主播原话。
4. 原始逐字稿、审核逐字稿、结构化母稿和 AI 候选必须分层保存。
5. 其他录播只能产生候选辅稿，不能自动覆盖正式母稿。
6. 分数只决定候选队列准入，不等同于人工审核通过，也不证明真实成交归因。
7. 所有母稿和辅稿内容必须能追溯到来源视频、时间范围和逐字稿证据。
8. 正式母稿按版本发布，历史版本不可覆盖，必须支持差异查看和回退。

## 3. 当前能力与缺口

当前系统已经能够：

- 为录播或导入视频生成带时间戳逐字稿；
- 保留 ASR 原稿、校准稿和人工校稿状态；
- 发现成交、疑似成交、问价、转品和讲得散等候选片段；
- 对片段生成 0 至 100 的推荐分和小白可读复盘；
- 保存候选片段的视频时间范围和逐字稿证据。

当前系统尚不能：

- 把整场多商品直播构建为正式母稿；
- 从 Obsidian 检索母稿并定位对应商品与话术阶段；
- 以母稿对应章节作为基准评分；
- 用高于 85 分的确定性规则控制候选辅稿准入；
- 持久化候选辅稿及其审核状态；
- 将人工批准的辅稿合并为新的母稿版本。

## 4. 内容分层

### 4.1 ASR 原始逐字稿

- 保存识别服务返回的原始文字和时间戳。
- 创建后不可覆盖。
- 仅用于审计、排错和前后版本比较。

### 4.2 审核逐字稿

- 使用公司参数卡、热词、替换词和受约束模型校对。
- 允许修正商品名、品牌、型号、数字边界、标点和明显错误断句。
- 价格、库存、优惠、成色、链接号和成交状态不得根据上下文猜测。
- 关键事实存在不确定项时必须进入人工确认。

### 4.3 结构化整场母稿

- 保留主播真实表达和原有成交逻辑。
- 删除纯静音、无意义重复和不承载业务信息的场控噪声。
- 按整场直播顺序组织开场、商品模块、转品模块和收尾。
- 每个段落保留来源时间范围，并链接到审核逐字稿。
- 第一版不允许大模型润色或重写主播表达。

### 4.4 场景应对话术

随机发生的成色询问、型号比较、价格异议、售后顾虑、库存异常和链接问题不强行写入固定流程。系统将其整理为带触发条件、动态字段和禁用条件的场景应对模块。

### 4.5 候选辅稿

- 来源必须是后续录播中的真实片段。
- 必须关联母稿版本、母稿章节、商品、来源视频和时间范围。
- 高于 85 分仅进入候选队列，状态为 `pending_review`。
- 人工批准后才允许申请合并到母稿新版本。

### 4.6 AI 优化候选

任何改变主播句式或新增表达的内容必须单独标记为 `ai_rewrite_candidate`。它不是主播原话，不参与首版自动准入，也不能未经人工确认进入正式母稿。

## 5. 整场母稿结构

业务上是一份整场母稿，存储上采用“整场索引 + 可维护模块”：

```text
10-企业母稿/
└── MS-001-整场直播母稿/
    ├── MS-001-整场母稿-V1.0.md
    └── MS-001-模块/
        ├── 01-开场与留人.md
        ├── 02-商品A.md
        ├── 03-商品A转商品B.md
        ├── 04-商品B.md
        └── 99-整场收尾.md

11-场景应对/
├── 成色询问/
├── 型号比较/
├── 价格异议/
├── 售后顾虑/
└── 链接与库存异常/
```

整场索引保存模块顺序、当前版本、来源直播和审核信息。商品模块至少包含：

- 商品标准名称和参数卡 ID；
- 直播阶段；
- 母稿话术；
- 主播原话；
- 来源视频和时间范围；
- 使用目的；
- 适用条件和禁用条件；
- 动态字段；
- 审核状态。

## 6. 母稿视频处理流程

目标母稿视频约六小时，不能作为单次不可恢复任务处理。流程如下：

1. 用户导入视频并明确选择“设为母稿来源”。
2. 系统读取时长、音视频轨道和文件指纹，创建母稿构建任务。
3. 音频按固定时长分块，并保留整场绝对时间轴和少量重叠上下文。
4. 根据直播标题、已识别文本和人工补选结果筛选公司参数卡。
5. ASR 前注入相关品牌、商品、型号和别名热词。
6. ASR 后执行确定性术语纠错，再执行受约束上下文消歧。
7. 合并分块结果并处理重叠字幕，生成整场审核逐字稿。
8. 根据商品切换、话术目标和时间顺序形成母稿章节候选。
9. 用户在预览页确认章节、商品和关键事实。
10. 写入 Obsidian，重新读取校验成功后发布母稿 V1.0。

每个分块独立记录状态和内容哈希。任务中断后从最后一个成功分块继续，不重新处理已完成分块。

## 7. 参数卡职责

公司确认的参数卡是 ASR 标准词库，不进入逐条知识审核队列。格式正确且处于启用状态的参数卡可以用于：

- ASR 热词；
- 标准商品名和型号匹配；
- 商品别名归一化；
- 常见识别错误替换；
- 型号、数字和成色边界拆分；
- 多个候选商品之间的上下文消歧。

参数卡不能授权系统推测动态价格、库存、优惠、链接号或实际成色。

## 8. 后续录播分析流程

```text
后续录播
→ 审核逐字稿
→ 发现成交候选片段
→ 识别商品和话术阶段
→ 检索当前正式母稿对应章节
→ 对照片段与母稿
→ 执行硬性准入检查
→ 计算母稿对比评分
→ 高于 85 分进入候选辅稿
→ 人工审核
→ 创建母稿新版本
```

无法找到母稿对应商品或章节时，不生成相对母稿分数，标记为“未匹配母稿”，允许人工指定章节后重新评分。

## 9. 硬性准入条件

评分之前必须全部满足：

1. 审核逐字稿的关键纠错已经处理。
2. 能确定商品和母稿对应章节。
3. 来源片段具有完整上下文和稳定时间范围。
4. 商品、型号、价格、库存、优惠和链接号不存在未解决冲突。
5. 标记为成交片段时，必须存在明确成交确认、锁货、备注、恭喜下单或可匹配订单证据。
6. 候选内容主要来自主播真实表达，不是只有 AI 改写结果。
7. 候选内容不与现有母稿重复，也不违反母稿的适用条件。

任一条件不满足时，状态为 `blocked` 或 `needs_confirmation`，不得因模型高分进入候选辅稿。

## 10. 母稿对比评分

| 评分项 | 分值 | 判断内容 |
|---|---:|---|
| 成交证据 | 25 | 是否存在明确下单、锁货、备注或成交确认 |
| 相对母稿提升 | 25 | 是否比母稿对应章节更清楚、更有说服力或补足缺口 |
| 话术可复用性 | 20 | 在相同场景或同类商品中是否可以重复使用 |
| 表达完整度 | 15 | 是否包含必要的引导、解释、异议处理和推进动作 |
| 事实准确性 | 10 | 商品和商业事实是否有来源且没有编造 |
| 场景明确度 | 5 | 是否说明触发条件、适用条件和禁用条件 |
| 总分 | 100 | 仅在硬性准入通过后有效 |

分数分流：

- `86-100`：自动进入候选辅稿队列；
- `70-85`：保留在复盘，可由人工申请进入候选；
- `0-69`：普通复盘，不进入辅稿；
- 未通过硬性准入：不论模型分数多少都不能进入候选。

评分结果必须展示各项分数、引用证据、对应母稿内容和差异理由，不能只显示总分。

## 11. 候选辅稿内容

候选辅稿至少包含：

```yaml
id: SS-商品键-日期-序号
type: support_script_candidate
status: pending_review
score: 91
master_script_id: MS-001
master_version: 1.0.0
master_section_id: PRODUCT-SECTION-ID
source_id: TR-来源直播ID
source_time_range: 01:22:10-01:23:36
```

正文必须包括：

- 对应母稿章节；
- 母稿当前话术；
- 主播原话；
- 相比母稿的提升；
- 建议加入位置；
- 适用条件和禁用条件；
- 动态字段；
- 事实核验项；
- 分项评分和证据。

## 12. 人工审核与版本升级

候选辅稿审核操作为：

- `通过并加入新版本`；
- `保留候选`；
- `退回修改`；
- `不采用`。

“通过并加入新版本”必须先展示母稿前后差异。确认后创建新版本，例如 V1.0 到 V1.1；旧版本保持不变。新版本记录审核人、审核时间、候选辅稿 ID 和变更章节。

## 13. 小白界面

录播分析仍采用三栏布局：

- 左栏：视频和候选片段；
- 中栏：带时间戳审核逐字稿；
- 右栏：母稿对比和评分。

右栏按以下顺序显示：

1. 是否通过准入检查；
2. 对应母稿位置；
3. 总分和分项分数；
4. 这段比母稿好在哪里；
5. 还需要确认什么；
6. 主播原话与母稿对照；
7. `加入候选辅稿` 或阻断原因。

不向普通用户展示原始模型 JSON、内部提示词和英文状态值。

## 14. 失败与一致性处理

- ASR 分块失败：保留已完成分块并允许单块重试。
- 参数卡无法读取：提示降级状态，禁止静默以低质量结果继续发布母稿。
- 母稿未发布：允许普通片段复盘，不允许生成相对母稿分数。
- 母稿章节匹配不确定：要求人工选择后重新评分。
- 模型输出非法：不生成候选，保留请求上下文并允许重试。
- Obsidian 写入失败：候选留在本地审核队列，母稿版本不变化。
- 母稿在评分后发生升级：候选标记为“基准已更新”，必须基于新版本重新评分。
- 同一片段重复分析：根据来源、时间范围和内容哈希去重。

## 15. 验收标准

1. 六小时级视频可以分块转写、断点续传并生成统一时间轴。
2. 公司参数卡参与 ASR 热词和术语纠错，但不推测动态商业事实。
3. 系统生成一份整场母稿索引及按顺序排列的商品、转品和场景模块。
4. 所有母稿段落均可回到来源视频和审核逐字稿。
5. 后续录播片段评分时必须加载明确的母稿版本和对应章节。
6. 评分展示六个分项及证据，总分可复算。
7. 总分 85 不自动进入候选，总分 86 且通过全部准入条件时进入候选。
8. 未通过硬性准入的片段不会因高模型分数进入候选。
9. AI 改写内容和主播原话在存储及界面上明确分离。
10. 候选辅稿不能直接覆盖母稿，人工确认后才创建新版本。
11. 写入失败或处理中断不会损坏原视频、逐字稿或历史母稿。

## 16. 首版范围

首版包含：

- 整场母稿来源导入；
- 分块 ASR 和可恢复任务；
- 参数卡辅助术语纠错；
- 审核逐字稿；
- 多商品母稿结构化；
- 母稿章节检索；
- 母稿对比评分；
- 高于 85 分的候选辅稿队列；
- 人工审核和母稿版本升级。

首版不包含：

- 大模型自动改写正式母稿；
- 未经审核自动合并辅稿；
- 仅凭话术评分推断真实成交归因；
- 多人并发编辑和复杂审批流；
- 自动发布到直播提词器或外部平台。
